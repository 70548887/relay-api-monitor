# Release v1.6.3 - 修复列表顺序与时间精度

## 发布信息

- 类型：正式修复版本；Tag `v1.6.3`，版本来源为根目录 `VERSION`。正式发布状态与时间以 GitHub Release 为准。
- 支持 Windows amd64、Linux amd64 和 Linux arm64。数据库仍为 Schema 4，launcher 协议 2、`usage_guard: 1` 与 `restore_v1` 能力要求不变。
- 延续 v1.6.2 的 Linux 在线升级暂存文件执行权限修复；正在运行 v1.5.1／v1.6.0 的 Linux 实例无法在安装新版之前自动获得修复，必要时按[旧版恢复步骤](https://github.com/70548887/relay-api-monitor/blob/v1.6.3/docs/UPDATES.md#旧版-linux-暂存文件权限失败的恢复)处理。

## 列表顺序修复

- 平台、分组、模型保留管理员的“排序”值升序；值相同时按创建时间倒序显示，时间仍相同时以 ID 升序固定顺序。调整名称不会改变同一排序值内的先后。
- 普通用户和管理员列表按创建时间倒序；相同时间以 ID 倒序固定顺序。
- 用户保存的连接从 JSON 中读取完整创建时间进行倒序比较，保留小数秒精度；同一时间以 ID 倒序固定顺序。
- 检测结果和作品记录在创建时间相同的情况下以 ID 倒序固定顺序。已有任务、备份、审计、在线测试列表的倒序规则经核对继续保留。
- 前端创建平台、分组、模型及同步模型后重新读取列表，统一使用服务端的人工排序与创建时间顺序。
- 云备份浏览器仅将本次已扫描、已加载的候选按修改时间倒序显示；S3 的 continuation 扫描范围保持原样，不承诺未扫描的云端对象也已纳入排序。
- 固定模板和执行计划的既有顺序、任务领取的先到先执行语义保持原样。以上按各接口现有的筛选与分页范围显示；不代表所有记录都会被一次查询返回，也不保证并发写入时基于 OFFSET 的分页位置固定。

## 安装与升级

1. 升级前保存数据库与 `master.key` 的受限安全快照，并保管离线恢复私钥；保留既有配置和持久数据目录。
2. 原生部署从 v1.6.2 升级时可用后台在线升级或同架构的完整安装包。若仍运行 v1.5.1／v1.6.0 Linux 程序并遇到暂存文件 `permission denied`，请先按[升级说明](https://github.com/70548887/relay-api-monitor/blob/v1.6.3/docs/UPDATES.md#旧版-linux-暂存文件权限失败的恢复)核对和处理确切缓存，或通过受控维护部署可信完整包；旧版重新下载不会自动修复权限。
3. Docker／宝塔容器部署须重建目标版本镜像和容器，保留原持久卷。升级后核对网站与 Worker 的实际版本及健康状态。

## 附件与校验

稳定 Release 固定 **11 个附件**：Windows amd64、Linux amd64、Linux arm64 各有服务端和 launcher 裸可执行文件，共 6 个；Windows 完整 ZIP 和两个 Linux 完整 tar.gz，共 3 个；另有 `manifest.json` 和 `SHA256SUMS`。

- Windows：`relaylab-windows-amd64-1.6.3.zip`
- Linux x86_64：`relaylab-linux-amd64-1.6.3.tar.gz`
- Linux ARM64：`relaylab-linux-arm64-1.6.3.tar.gz`

Manifest 须包含与 Tag 一致的版本、完整源码 Commit、统一 UTC 构建时间、Schema 4、launcher 协议 2、`usage_guard: 1`、最低 Schema 1，以及各平台附件的大小与 SHA-256。`SHA256SUMS` 覆盖 9 个程序／压缩包和 Manifest。流水线先上传草稿、下载并逐项校验，再发布正式版。完整包不包含数据库、`master.key`、真实本机配置、Token 或日志。
