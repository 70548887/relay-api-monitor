# Release v1.6.2 - 修复 Linux 在线升级暂存文件权限

## 发布状态与兼容范围

- 类型：正式修复版本；Tag `v1.6.2`，版本来源为根目录 `VERSION`。正式发布时间以 GitHub Release 为准。
- v1.6.1 Tag 已推送，但该次发布被新增 npm 安全告警阻止，未形成通过门禁的正式 Release。保留已推送的 Tag 及其说明，不覆盖或改写；本次修复使用新版本 v1.6.2。
- 支持 Windows amd64、Linux amd64、Linux arm64。Go 构建基线为 1.26.11；数据库仍为 Schema 4，launcher 协议 2、`usage_guard: 1` 和 `restore_v1` 能力要求不变。

## 修复

- Linux 在线更新旧版下载器以 `os.CreateTemp` 创建 `0600` 暂存文件。即使大小与 SHA-256 正确，launcher 在替换前执行 `version --json` 仍会因没有可执行位而得到 `permission denied`。本版保留 v1.6.1 源码的修复：仅在完整下载并校验大小、SHA-256 成功后，对该临时文件设置 `0700`，检查结果，再提交为可安装状态。对旧缓存先重新核对私有路径、普通文件、大小和 SHA-256，再通过已打开的文件句柄修复所有者可执行位；校验失败不提升权限、不安装。
- Windows 真实二进制升级测试曾在持久化的 `succeeded` 事务刚写入、维护文件尚未删除时立即写入业务数据，收到 503。事务先持久提交再解除维护是产品的必要顺序；回归现要求独立等待 launcher 状态为 `running`、维护为 false 且网站和 Worker 都运行，然后才单次执行验证写入，不通过重试写请求隐藏错误。

- GHSA-fc5q-39xc-vjpf、npm advisory source `1247710`：picomatch 4.0.7 及更早版本的特定 glob 可导致 ReDoS。当前锁文件中的受影响依赖链包括 `picomatch`、`fdir`、`tinyglobby`、`vite`、`vitest`、`@vitejs/plugin-react`，均仅用于开发、构建或测试；截至编写时上游没有已发布的修复版本。这仍是构建链风险，不宣称完整 npm 审计零告警。
- [审计脚本](https://github.com/70548887/relay-api-monitor/blob/v1.6.2/scripts/audit_npm.py)应先要求生产依赖审计无发现；完整审计只允许唯一 source `1247710` 沿 `via` 链传播、受影响节点均在锁文件中明确标记为开发依赖，且例外绑定最终锁文件的 SHA-256。新增任何其他告警、生产依赖命中、锁文件与报告不符或审计失败均阻止发布。例外到 `2026-11-25T00:00:00Z` 自动失效；届时须重新评估并优先升级到上游修复版本。不能使用全局关闭审计或 `npm audit fix --force` 降级工具链代替门禁。
- Node/npm 只在前端构建与测试阶段运行。Docker 最终运行层仅包含 Go 程序与已构建的静态资源；Go 通过 embed 提供页面。生产依赖审计当前无发现，但构建环境仍须控制输入来源并关注上游修复。

## 安装与旧版恢复

1. 升级前保存数据库及 `master.key` 的受限快照，并保管离线恢复私钥。确认当前 launcher、程序架构与目标 Release 的 Manifest 兼容；Docker／宝塔容器部署通过重建镜像和容器更新，保留数据卷。
2. 正在运行的 v1.5.1／v1.6.0 Linux 程序无法依靠尚未安装的修复自动升级。如果其下载完成后执行 `version --json` 报权限错误，按[旧版 Linux 恢复步骤](https://github.com/70548887/relay-api-monitor/blob/v1.6.2/docs/UPDATES.md#旧版-linux-暂存文件权限失败的恢复)：核对最终下载的确切暂存文件、可信 Manifest 的大小与 SHA-256，单文件设置 `0700`，在后台重新检查到同一目标为 `ready` 后安装。修复权限后不要重新下载，旧版会再次生成 `0600` 文件。
3. 即使权限为 `0700` 仍不能运行时，应检查父目录权限、服务用户及挂载点 `noexec`；`chmod` 无法修复 `noexec`。不要对目录递归 chmod，也不要设 `777`。若暂存路径或摘要不匹配，停止安装并通过受控维护流程获取可信完整包。
